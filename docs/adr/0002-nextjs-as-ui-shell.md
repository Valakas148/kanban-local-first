# 2. Next.js як тонка UI-оболонка

- **Дата:** 2026-11-02
- **Статус:** Прийнято (Accepted)

## Контекст

Застосунок local-first (див. [ADR-0001](0001-use-local-first-architecture.md)): дані живуть в IndexedDB у браузері, тож сервер їх не бачить і не може відрендерити дошку. Для основного UI SSR майже нічого не дає.

Водночас Next.js уже знайомий, добре поєднується з Tailwind, shadcn/ui та TanStack Query і знадобиться для публічних сторінок (лендинг, пізніше шаринг дошки за посиланням). Окремо планується вивчення бекенду.

## Рішення

1. Next.js (App Router) використовується як тонка оболонка для UI. `src/app/` містить лише файли роутингу (`page.tsx`, `layout.tsx` тощо), які збирають екрани з `features/`.
2. Усе, що торкається локальної БД, виконується на клієнті (`'use client'`, за потреби `dynamic(..., { ssr: false })`).
3. SSR застосовується лише для публічних сторінок, якщо вони з'являться.
4. Бекенд робиться окремим сервісом, а не через route handlers чи server actions Next.js.

## Альтернативи

- **Vite + TanStack Router (SPA):** простіший для суто клієнтського застосунку, але це новий інструмент. Оскільки роутинг ізольований у `src/app/`, перехід залишається дешевим.
- **Route handlers / server actions Next.js як бекенд:** відхилено. Мета вивчити окремий бекенд, а sync-протокол не має залежати від UI-фреймворку.

## Наслідки

- **Плюси:** знайомий інструмент; SSR доступний для публічних сторінок; логіка в `features/` не залежить від фреймворку.
- **Мінуси / складнощі:** частина можливостей Next не використовується; треба уникати hydration-помилок і звернень до IndexedDB на сервері.
- **Відкрите питання:** чи вмикати статичний експорт (`output: 'export'`); вирішується під час роботи над PWA.
